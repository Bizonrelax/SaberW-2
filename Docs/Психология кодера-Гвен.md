## 1. Психология кодера

### Сильные стороны
1. **Диагност с руками.** Умеет строить трассировку рефлексией (Dbg3) и нашёл-таки первопричину: `findPhrases candidates (0)` из-за сброса ранов на любом SEPARATOR. Когда он трассирует — он точен.
2. **Честен.** Никогда не рисует зелёное вместо красного. Пишет «задача частична», «квота исчерпана», «код не компилируется», ставит «⚠️ критическое предупреждение о целостности». Такому можно доверять отчёт без перепроверки каждого слова.
3. **Исполнителен к точному коду.** Просил дать `countRawOccurrences` готовым — вставил «ровно ваш код» без самодеятельности. Точные сниппеты он применяет хирургически.
4. **Ресурсен в окружении.** Сам ставит Maven/JDK 21 через adoptium, обходит битый apt, лечит опечатки sed'ом, чинит OOM дедупликацией `seenInRun`.
5. **Соблюдает защитные правила**, если они сформулированы: в 13m14s увидел staged-перенос и сделал WIP-коммит вместо отката — ровно по инструкции.
6. **Качественные комментарии.** Пояснения к exact-span семантике лучше, чем были в исходнике.

### Слабости
1. **Марафонщик без чек-поинтов.** Берёт объём «шесть шагов за прогон» и умирает на шаге 4, оставляя дерево без финального коммита. Коммит для него — «финальный акт», а не страховка.
2. **Рефлекс переписывания.** На красный тест отвечает сменой архитектуры (три разных матчинг-машинерии за три сессии), а не бисекцией по трассировке. В 5m17s этим же рефлексом **уничтожил перенос** (`git checkout --` по staged-диффу прошлой сессии).
3. **Поздняя верификация.** Правит пачками, компилирует раз, тесты гонит в конце. Свою же Dbg3 в следующей сессии не перезапустил — инструмент брошен после постройки.
4. **Дриф сигнатур и мертвяка.** `wordParts`→`wordsOf`, `countSpanTokens` не определён, `k++++`, `w.size()` вместо `ids.size()`, три варианта `chooseReplacement` за сессию. Компиляция достигается ремонтными кругами, а не дисциплиной.
5. **Гипотеза без подтверждения.** «Подозреваемый №3 с вероятностью 90%» — и ушёл по квоте, не проверив трассировкой. Проверку передаёт следующей сессии как долг.
6. **Амнезия окружения.** Каждый прогон заново открывает, что mvn нет и JDK 17, тратит на это 8–10 вызовов.
7. **Отчёт-простыня.** 240 страниц эхо-команд; суть — в последних 15 строках.

### Поведение по ситуациям
| Ситуация | Реакция |
|---|---|
| Маленькая задача + готовый сниппет | Быстро, точно, зелёно |
| Большая размытая задача | Долго читает весь код, жжёт квоту, полу-реализация |
| Красный тест | Качается «откат ↔ переписывание», без стопа и трассировки |
| Давление квоты | Честный итог + список долгов, но часто без коммита |
| Явное защитное правило («не откатывай», «закоммить WIP») | Соблюдает буквально |

Вывод: **кодер — сильный тактик и слабый проект-менеджер себя.** Всю менеджерию (чеки, стоп-правила, объём прогона) должен делать промт.

## 2. Что обязано быть в промте

1. **Одна цель на прогон** + «определение готовности» точными командами и ожидаемым выводом (`mvn -q test` → `Failures: 0` кроме 3 @Disabled).
2. **Бутстрап окружения первой строкой** и требование создать `/workspace/env.sh` (`export JAVA_HOME=... PATH=...`) и дальше только `source env.sh` — лечит амнезию.
3. **Микро-шаги с чек-поинт-коммитами**: после каждого зелёного состояния коммит с заданным сообщением. Коммит = страховка переноса, а не финал.
4. **Готовый код для всего нетривиального.** Описания он додумывает; сниппеты — вставляет. Запрет отклоняться от сниппета без стопа и доклада.
5. **Цикл верификации после каждой правки**: `compile` после каждой, `test -Dtest=Имя` после шага, полный набор только на чек-поинте.
6. **Правило «трассировка раньше переписывания»**: красный после микро-фикса → прогнать Dbg/временный тест с печатью стадии, вставить вывод в отчёт; запрещение менять архитектуру без трассировочного доказательства.
7. **Тест раньше фикса** для багов: сначала падающий регрессионный кейс, потом лечение — объективный критерий вместо «кажется починил».
8. **Список «НЕ»**: не откатывать перенос; не трогать файлы вне списка; не вводить вторую матчинг-машинерию; не рефакторить сверх диффа; не публиковать/не merge.
9. **Протокол конца квоты**: за 3 вызова до лимита — коммит `WIP: ...` **и файл `REMAINING.md` в коммите** (состояние переезжает через git, а не через память чата); в начале следующей сессии читать его первым.
10. **Формат отчёта ≤ 30 строк**: таблица шаг→статус→хвост вывода, хэши коммитов, список долгов.
11. **Одно абзацное «зачем»** в начале: поняв смысл, он пишет верные комментарии и не портит семантику по дороге.

## 3. Шаблон промта

```
ЦЕЛЬ (1 строка): <что должно стать истинным после прогона>
ГОТОВНОСТЬ: <команда 1> → <ожидаемый вывод>; <команда 2> → <ожидаемый вывод>
КОНТЕКСТ (3–5 строк): почему; что уже известно (трассировка/гипотеза); какие файлы трогать; какие НЕ трогать.
ОКРУЖЕНИЕ: [ -f /workspace/env.sh ] || cat > /workspace/env.sh <<'EOF' ... EOF; source /workspace/env.sh
ШАГИ (нумерованные микро-шаги):
  N. действие; [точный код, если нетривиально]; проверка: <команда> → <ожидание>; чек-поинт: git commit -m "<сообщение>"
СТОП-ПРАВИЛА: красный после микро-фикса → трассировка (вывод в отчёт), архитектуру не менять; нужна девиация от сниппета → стоп и доклад; осталось ~3 вызова → протокол конца.
ЗАПРЕТЫ: не откатывать staged/рабочие изменения прошлых сессий; не создавать параллельные механизмы; не трогать <список>; не публиковать.
ПРОТОКОЛ КОНЦА: коммит WIP + REMAINING.md в коммите; отчёт ≤30 строк: шаги/статус/хвосты вывода/хэши/долги.
```

## Наработанные правила взаимодействия (по состоянию на 18.10.2026)

### Каналы публикации
- Кодер пишет изменения в /workspace контейнера. У него нет git-remote и токена Гитхаб по умолчанию.
- Кнопка «Опубликовать на GitHub» в UI кодера работает нестабильно: с селектором ветки main срабатывает, с селектором рабочей ветки — часто гаснет без публикации.
- Надёжный канал — токен в первом сообщении сессии. По токену кодер выполняет fetch/push/PR программно.
- Кнопки UI («Опубликовать», «Разница») НЕ являются индикаторами состояния сессии. Индикатор — вывод git log и grep маркеров в файлах в отчёте кодера.

### Прогресс между сессиями
- Контейнер одноразовый: после сессии /workspace уничтожается.
- Все коммиты-чек-поинты пушатся в рабочую ветку (ptatimon-N) немедленно, даже если тесты красные (WIP-протокол).
- Следующая сессия клонирует рабочую ветку и продолжает с WIP-коммитов.
- Потеря контейнера = потеря только незакоммиченного состояния; вся опубликованная работа живёт в ветке.

### Промты: файлы vs чат
- Тяжёлые промты (многошаговые, со сниппетами, с маркерами комментариев) оформляются файлами в Docs/prompts/.
- Файл-промт создаётся в той ветке, где будет запущен (селектор чата = целевая ветка).
- В чат отправляется только однострочник-указатель: «Прочитай в репозитории файл Docs/prompts/… и выполни шаги».
- Тяжёлый промт в теле чата часто падает с ошибкой соединения (предположительно фильтр payload); файл-канал устойчив.

### Защита от рассинхрона веток
- Промт-файл начинается с ШАГА 0: grep-проверка базовой линии (маркеры предыдущих сессий должны присутствовать).
- Если маркеры отсутствуют → STOP, ничего не править, доклад владельцу. Это канарейка: ветка отстала от main или работа потеряна.
- Все слияния веток — только через GitHub (PR/веб); в промт-файлах merge-инструкции запрещены, контейнер не имеет remote.

### Формат отчёта
- Отчёт ≤30 строк. Последние две строки строго:
  СОСТОЯНИЕ: ЗЕЛЕНО|КРАСНО (tests: пройдено/всего, skipped Z)
  ВЕРДИКТ: ПУБЛИКОВАТЬ|НЕ ПУБЛИКОВАТЬ — причина ≤10 слов.
- ВЕРДИКТ определяет следующее действие владельца. Красный = ничего не публиковать, собирать дельта-промт.

### Токены
- Только fine-grained, только на один репозиторий (SaberW-2), expiration 7 дней.
- Permissions: Contents: Read and write + Pull requests: Read and write.
- Токен — расходник: при компрометации отзывается и перевыпускается за ~5 минут.
- В отчётах кодера токен маскируется до последних 4 знаков; в файлы, .git/config, историю команд не пишется.

### Что НЕ работает
- git fetch/merge/pull/remote add в контейнере без токена (контейнер не имеет remote по умолчанию).
- Переключение ветки внутри чата (селектор фиксируется при создании чата).
- Ручное редактирование документов ТЗ владельцем — эту работу делает кодер через промт-файл.
- Публикация по кнопке с селектором, отличным от main — ненадёжна.
